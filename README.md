# BOM-App — دموی فارسی سیستم مدیریت BOM

نسخه اولیه مستقل از دیتابیس، ساخته‌شده با **React + Vite**. رابط فارسی RTL و داده‌های نمونه از فایل‌های JSON بارگذاری می‌شوند.

## شروع سریع در سیستم شخصی

```bash
npm install
npm run dev
```

پس از اجرا، آدرس نشان‌داده‌شده در ترمینال را باز کنید.

## راه‌اندازی GitHub Pages در مخزن BOM-App

1. محتوای **داخل پوشه `BOM-App`** فایل ZIP را در ریشه مخزن GitHub آپلود کنید؛ فایل `package.json` باید در ریشه Repo باشد.
2. اگر مخزن تازه است، شاخه اصلی را `main` بگذارید.
3. در GitHub به **Settings → Pages → Build and deployment** بروید و **Source: GitHub Actions** را انتخاب کنید.
4. فایل workflow موجود در `.github/workflows/deploy.yml` در هر Push به `main` سایت را Build و منتشر می‌کند.
5. پس از سبزشدن workflow در **Actions**، آدرس دمو از بخش Pages قابل مشاهده است.

> اگر هنگام آپلود با GitHub Web گزینه Hidden files در پوشه `.github` به‌درستی منتقل نشد، می‌توانید فایل workflow را به‌طور جداگانه ایجاد کنید یا مخزن را با Git آپلود کنید.

## ساختار داده

- `public/data/items.json`: بانک اقلام یکتا
- `public/data/suppliers.json`: تأمین‌کنندگان
- `public/data/quotations.json`: تاریخچه استعلام‌ها و قیمت‌ها
- `public/data/assemblies.json`: ماژول‌ها و سامانه‌ها
- `public/data/projects.json`: پروژه‌ها و BOM پروژه

## رفتار ذخیره‌سازی

GitHub Pages یک میزبان **ایستا** است و فایل‌های JSON موجود در مخزن را از مرورگر تغییر نمی‌دهد.

- اولین اجرا: داده‌های نمونه از `public/data/*.json` خوانده می‌شوند.
- هر تغییر: در `localStorage` همان مرورگر ذخیره می‌شود.
- انتقال داده: با «خروجی JSON» یک پشتیبان بگیرید و روی دستگاه دیگر از «ورود JSON» استفاده کنید.
- برای ویرایش داده‌های نمونه مشترک سایت، فایل‌های مخزن را اصلاح و دوباره Deploy کنید.
- **هشدار:** داده محرمانه یا قیمت واقعی را در مخزن عمومی یا دموی عمومی ذخیره نکنید.

## محدودیت‌ها و نکات مهم دمو

- نسخه `0.1` نمونه کاربردی برای بررسی جریان کار است، نه سامانه عملیاتی یا حسابداری.
- قیمت‌ها و مشخصات نمونه ساختگی/آزمایشی‌اند.
- درخت BOM بازگشتی و انتخاب قیمت به تفکیک مسیر وقوع پیاده شده است.
- `Reference` به ساختار یکسان اشاره می‌کند. `Duplicate` تعریف مستقلی می‌سازد؛ **برای سفارشی‌سازی ساختارهای کپی‌شده از بخش افزودن جزء استفاده کنید**.
- قیمت جدید پیشنهادی از آخرین استعلام ثبت‌شده قلم گرفته می‌شود؛ در نسخه عملیاتی باید اعتبار، MOQ، ارز، شرایط حمل و سیاست انتخاب تأمین‌کننده کنترل شوند.
- هزینه نمونه فقط مجموع قیمت اقلام است؛ خدمات، هزینه ساخت، مالیات، حمل، نرخ تبدیل ارز و قیمت‌گذاری Fixed هنوز پیاده نشده‌اند.
- تاریخچه برآورد و Baseline در JSON ذخیره می‌شود؛ قابلیت ویرایش Baseline در رابط وجود ندارد، ولی این نسخه امنیت سروری و تضمین تغییرناپذیری واقعی ندارد.
- یک پروژه فعلاً با شیوه ساده‌سازی‌شده قیمت‌گذاری از روی مسیر BOM کار می‌کند؛ با ساختارهای بسیار پیچیده و تغییر نسخه مرجع، به مدل Usage Instance و Migration قیمت نیاز است.
- درخواست استعلام و ارجاع کار در نسخه‌های بعدی اضافه می‌شود.

## فناوری و ساختار

`React 19`، `Vite 6`، `lucide-react` و CSS اختصاصی RTL، بدون Backend و دیتابیس.

مجوز: نمونه داخلی آزمایشی؛ پیش از استفاده تجاری، شرایط مجوز وابستگی‌ها را بررسی کنید.


## نسخه 0.2: نمایش تعداد در BOM

در درخت پروژه، ستون «تعداد در والد» قابل ویرایش است و «تعداد کل» حاصل‌ضرب تعداد در تمام سطوح است. هزینه هر ردیف نیز از تعداد کل محاسبه می‌شود. در کتابخانه ماژول‌ها و سامانه‌ها، جزئیات اجزا و تعداد مستقیم آن‌ها قابل مشاهده است. تغییر تعداد جزء در یک Reference ساختار مشترک را تغییر می‌دهد و بر همه استفاده‌های آن ساختار مؤثر است.

برای بازگردانی داده‌های نسخه جدید اگر داده‌های قبلی در مرورگر حفظ شده‌اند، از منوی تاریخچه «بازگردانی داده نمونه» استفاده کنید (تغییرات ذخیره‌شده مرورگر حذف می‌شوند).


## امکانات نسخه 0.3: گردش وضعیت و Audit Trail

- تعیین نام «ثبت‌کننده تغییرات» در نوار بالای برنامه؛ این نام در رویدادهای جدید استفاده می‌شود.
- مراحل وضعیت: `Draft → Estimate → Approved → Contracted → Archived`؛ از Estimate امکان بازگشت به Draft وجود دارد.
- انتخاب «تأیید نهایی و ثبت Baseline» به‌طور هم‌زمان وضعیت را Approved کرده و Snapshot ساختار و قیمت را ذخیره می‌کند.
- ویرایش تعداد، اضافه و حذف ردیف و اعمال قیمت در پروژه مصوب قفل است؛ ساختارهای مشترک با پروژه مصوب نیز قفل می‌شوند.
- «ساخت Revision کاری جدید» پروژه و تعاریف ماژول/سامانه درون آن را به نسخه مستقل تبدیل می‌کند.
- تمام تغییرات ثبت‌شده با قبل/بعد در زبانه «تاریخچه تغییرات» دیده می‌شوند، با فیلتر پروژه و نام ثبت‌کننده.
- Audit در خروجی JSON و LocalStorage حفظ می‌شود؛ رویدادها از زمان نصب نسخه 0.3 به بعد ثبت می‌شوند؛ گذشته قابل بازیابی نیست.

**هشدار مهم:** نسخه بدون سرور و احراز هویت فقط دمو است. نام کاربر، زمان کلاینت، محتوای LocalStorage و حتی Audit قابل دستکاری‌اند؛ بنابراین این ویژگی «ردیابی آزمایشی» است نه ممیزی قانونی و غیرقابل‌تغییر. برای محیط واقعی باید رویدادهای غیرقابل‌ویرایش، کاربر احراز هویت‌شده و تراکنش‌های سمت سرور پیاده‌سازی شوند. تغییر نام نمایشی کاربر قابلیت ثبت هویت معتبر محسوب نمی‌شود.

## نسخه 0.4 — صفحه خواناتر نسخه‌های پروژه
- نمایش کارت‌های نسخه با وضعیت مصوب/ثبت دستی، زمان، هزینه، ثبت‌کننده و تغییر مبلغ نسبت به نسخه قبل.
- بازکردن جزئیات اقلام، تعدادهای مؤثر و قیمت‌های ثبت‌شده در Snapshot.
- لینک سریع به صفحه تاریخچه فعالیت‌های پروژه.
- نسخه‌های قدیمی که از ابتدا اطلاعات تأییدکننده ندارند به‌عنوان «نامشخص» نشان داده می‌شوند؛ نام یا تأیید ساختگی تولید نمی‌شود.
- داده‌ها همچنان در LocalStorage ذخیره می‌شوند. قبل از به‌روزرسانی از داخل برنامه خروجی JSON بگیرید.


## v0.5 — میز کار و سند مرجع
- منوی «میز کار من»: داشبورد متناسب با نقش انتخاب‌شده
- منوی «وظایف و تأییدها»: ارجاع، وضعیت، مسئول و تأیید فنی/تجاری آزمایشی
- منوی «نقش‌ها و دسترسی‌ها»: ماتریس ساده مجوزهای دمو
- منوی «سند مرجع»: نمایش HTML جامع ۲۰ فصلی داخل پنل و امکان بازکردن جداگانه
- داده‌های وظایف در `public/data/tasks.json` شروع می‌شوند و سپس در LocalStorage ذخیره می‌شوند. اگر قبلاً نسخه‌های قدیمی را باز کرده‌اید، وظایف نمونه ممکن است به‌صورت خودکار به داده ذخیره‌شده قبلی تزریق نشوند؛ از JSON پشتیبان گرفته و در صورت نیاز بازگردانی داده نمونه انجام دهید.
- نقش انتخابی و نام ثبت‌کننده، قابل تغییر در رابط‌اند. **این مکانیزم احراز هویت واقعی نیست و برای اطلاعات محرمانه و گردش تأیید رسمی مناسب نیست.**
- برای تصویب پروژه نمونه، نقش مدیر فنی و مدیر بازرگانی باید در تب «وظایف و تأییدها» به‌ترتیب تأییدهای مربوطه را ثبت کنند؛ سپس مالک محصول می‌تواند تصویب نهایی را انجام دهد.


## تغییرات v0.6 — صفحه اختصاصی و جستجوی فرزند
- تفکیک شاخص اقلام، ماژول‌ها و سامانه‌ها بر اساس **تعریف‌های یکتا** (نه مجموع تعداد استفاده).
- انتخاب مجزای نوع فرزند (قلم، ماژول، سامانه، پروژه) با رعایت سلسله‌مراتب.
- جستجوی زنده نام/شناسه/MPN و انتخاب فرزند، همراه با تعداد در والد.
- صفحه اختصاصی قلم، ماژول، سامانه و پروژه از جدول‌ها و درخت BOM؛ مشخصات JSON، توضیحات، پیوند تصویر و دیتاشیت، BOM/استعلام و آخرین سوابق.
- پیوندهای تصویر و دیتاشیت در LocalStorage/خروجی JSON ذخیره می‌شوند؛ آپلود فایل واقعی بدون Backend پشتیبانی نمی‌شود.
- سند مرجع آخرین گزینه منوی پنل، پس از تاریخچه تغییرات است.

**توجه:** این نسخه از نسخه قبلی و کلید LocalStorage یکسان استفاده می‌کند؛ قبل از به‌روزرسانی خروجی JSON بگیرید. دسترسی‌ها نمایشی هستند؛ کنترل امن نقش‌ها و آرشیو فایل در نسخه تولیدی باید سمت سرور باشد.


## v0.8: مدیر مالکین محصول
- نقش `head_owner` تمام مجوزهای `owner` را به ارث می‌برد، به همراه portfolio, assign_owner, transfer_owner, escalation و reports.
- منوی «مدیریت مالکین محصول» برای ثبت مالک مسئول و تغییر آن؛ تغییرات در Audit Trail ذخیره می‌شوند.
- پروژه‌ها فیلدهای اختیاری `ownerName` و `managerName` دارند؛ JSONهای قدیمی سازگار می‌مانند.
- محدودیت حوزه مدیر با `managerName` در دمو شبیه‌سازی شده؛ پروژه بدون مدیر باید ابتدا تخصیص داده شود.
- تأیید فنی و تجاری همچنان اجباری است. در نسخه عملیاتی هویت کاربران و حوزه‌ها باید در سرور بررسی شوند.
- سند مرجع داخل پنل با فصل ۲۱ به‌روز شد.
